## Context

The static statistics site receives human-readable JSON generated by `BasketStatisticsExportService`. Existing personal files contain regression-based hole rows and the player lookup only includes players with eligible hole rows. Imported PDGA throw timelines are normalized into `round_result_throws`, with one record per score ordinal and fields for zone and distance.

The putting calculation must operate per player, round result, and hole. A throw record describes the position reached by that throw; therefore the record immediately before a basket record is the successful putting attempt. Penalty throws can create gaps in `score_ordinal`, so ordinal values must be sorted rather than assumed contiguous.

## Goals / Non-Goals

**Goals:**

- Calculate C1x and C2 successful and total attempt counts from normalized throw records.
- Export putting summaries for every player represented by imported throw data.
- Preserve the existing hole-statistics filters and table behavior.
- Add a Putting stats second-level view with exact two-decimal percentages.
- Keep the static export as the only data integration boundary.

**Non-Goals:**

- No new database tables or migrations.
- No changes to the PDGA throw import format.
- No course, round, or rating filters for Putting stats.
- No changes to existing regression or basket sliding-window calculations.

## Decisions

### Calculate attempts from ordered per-hole timelines

Load throw rows with their player and round-result relationships, group them by round result and hole ordinal, and sort each group by `score_ordinal`. Omit a hole unless its final record has `zone_id = 5`. For every preceding record, mark it successful when the next record has `zone_id = 5`; otherwise mark it unsuccessful. This handles penalty gaps and multiple missed putts without relying on score arithmetic.

### Apply zone-first classification with distance fallback

- Zone 4 records classify as C2 regardless of distance.
- Zone 3 records classify as C1x only when distance is 12–32 feet inclusive.
- A zone 3 successful record below 12 feet is ignored; a zone 3 unsuccessful record below 12 feet still contributes to the C1x total.
- Records from all other zones use `distance_to_target`, falling back to `drop_distance_to_target` only when the first value is null. Values from 12–32 feet classify as C1x and values from 33–65 feet classify as C2.
- Records without a qualifying zone or distance do not contribute.

This keeps the source units in feet while matching the requested meter zones at the specified inclusive boundaries.

### Keep putting data at player-snapshot level

Add a `putting` summary to each personal player JSON file rather than creating separate files. This keeps player selection and loading unchanged at the manifest level and allows the UI to switch between hole and putting views without another request.

The summary contains successful and total counts for C1x and C2. Percentages are calculated as successful divided by total and rounded to two decimal places for display. When total is zero, the UI displays `— (0 / 0)`.

### Separate player eligibility from hole-row eligibility

Build the player lookup from the union of players with eligible hole rows and players with imported throw rows that produce a personal snapshot. This ensures throw-only players can be selected while retaining the existing minimum-count behavior for Hole stats.

### Use nested tabs inside Personal stats

The top-level Personal stats tab retains one player selector labeled `Select a person to view statistics`. Before selection, second-level tabs and content remain hidden. After selection, show `Hole stats` and `Putting stats`; default to Hole stats. Course and minimum-count controls are rendered only for Hole stats. Putting stats renders only the two summary lines.

## Risks / Trade-offs

- [Incomplete or malformed timelines] → Omit only the affected hole when the final record is not zone 5 or required ordering data is unusable; continue aggregating other holes.
- [Zero denominators] → Preserve counts and display an em dash instead of claiming a 0.00% success rate.
- [Larger export query] → Fetch only the fields required for putting aggregation and aggregate in memory once per export; do not issue one query per player or hole.
- [Additional throw-only players] → Keep existing variation rows optional and render a clear empty Hole stats message while allowing Putting stats to work.
- [Export/UI schema drift] → Add focused export and static-page tests using representative success, miss, penalty-gap, invalid-hole, bullseye, and distance-fallback cases.
